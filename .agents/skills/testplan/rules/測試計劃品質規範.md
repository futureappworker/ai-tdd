# Rule 1 - 系統介面與呼叫契約

- 需求範圍內的每個系統介面必須各有一列表列與一個介面區段。
- 每個介面必須寫一次呼叫契約、公開操作、本介面涵蓋與留給其他介面。
- 公開操作必須寫出操作名稱、輸入欄位，以及成功或拒絕時可觀察的結果。
- 測試計劃不得包含測試程式碼、SQL 或斷言函式呼叫。

## Good Example

- 進入房間的操作寫出路徑、本體欄位與成功狀態，沒有測試程式碼。

```markdown
- `POST /api/rooms/enter`：本體欄位 `nickname`、`roomCode`。新建房間成功是 HTTP 201。
```

## Bad Example

- 同一項操作改寫成斷言程式碼，計劃不再只描述可觀察的契約。

```markdown
- assert.equal(response.status, 201)
```

# Rule 2 - 共用 Arrange Fixtures

- 兩個以上案例共用的前置狀態必須定義成共用 Arrange Fixture。
- Fixture 必須寫出可執行的前置操作，並保留後續呼叫需要的識別值。
- 案例的前置條件必須引用 Fixture 名稱。
- 當 Fixture 的字面值會改變本案例要分辨的輸入時，該段前置必須寫在該案例內，不得改寫共用 Fixture 來遷就這一個案例。

## Good Example

- 案例引用已定義的 Fixture，房號與玩家留在 Fixture。

```markdown
- **前置條件 ( Arrange )** Fixture 準備中。保留原 `roomId`。
```

## Bad Example

- 共用 Fixture 已能表達等待中的房主，案例仍把同一段進房步驟整段重寫一次。

```markdown
- **前置條件 ( Arrange )** 玩家A 呼叫 `POST /api/rooms/enter`，`nickname` 為「玩家A」，`roomCode` 為「1234」。
```

## Exceptions

- 案例要分辨的輸入與共用 Fixture 的字面值衝突時，該段前置寫在案例內。例如兩位玩家都必須使用「小明」，而共用 Fixture 的暱稱是「玩家A」。

# Rule 3 - 原子案例

- 一個案例必須只有一個唯一測試意圖。
- 一個案例要同時驗證兩個以上可分開觀察的結果時，必須拆成多個原子案例。
- 每個案例必須包含唯一測試意圖、受測部位、受測操作、前置條件、操作、觀測通道、預期輸出、必須維持不變、本案例不驗證、預期 RED 原因。
- 操作必須寫出這次送出的具體輸入，包含會影響規則判斷的字面值。
- 對應需求只索引規格。斷言要用的字面值必須寫在 Fixture、操作或預期輸出。

## Good Example

- 猜中後的勝負與祕密答案揭曉分成兩個案例，各自只有一個意圖。

```markdown
1. **案例 ( Case )** BE-8.1A 猜中時回饋 4A0B 且房主因猜中獲勝
2. **案例 ( Case )** BE-8.1B 猜中結束後雙方看得到彼此的祕密答案
```

## Bad Example

- 同一個案例同時要求勝負、祕密答案與猜測紀錄三個獨立結果。

```markdown
1. **案例 ( Case )** BE-8.1 猜中後結束、揭曉祕密答案並留下猜測紀錄
```

# Rule 4 - Oracle

- 預期輸出的每一項事實必須能對到該案例的觀測通道。
- 必須維持不變必須只列這次要斷言、且與操作前相同的欄位；沒有時必須寫「無」。
- 本案例不驗證列出的項目不得寫進預期輸出或必須維持不變。
- 每個案例必須寫預期 RED 原因，指出這個案例尚不存在時會失敗的觀察。

## Good Example

- 拒絕案例只斷言這次的拒絕訊息，並把相鄰規則放在本案例不驗證。

```markdown
- **預期輸出 ( Expected Output )** HTTP 400。`message` 為「尚未輪到你，請等對手猜完。」
- **必須維持不變 ( Must Stay )** `turn` 仍是房主。`guesses` 仍是空的。
- **本案例不驗證 ( Not Verified )** 1325 對 1234 的 1A2B、不合法猜測 1123。
```

## Bad Example

- 本案例不驗證已排除 1A2B，預期輸出仍要求這個分數。

```markdown
- **預期輸出 ( Expected Output )** HTTP 400。`result` 為 1A2B。
- **本案例不驗證 ( Not Verified )** 1325 對 1234 的 1A2B。
```

# Rule 5 - TDD 順序

- TDD 順序必須列出每個原子案例恰好一次。
- TDD 順序是執行順序，不必與情境章節順序相同。
- 順序中的每個項目必須對到一個已寫出的案例。

## Good Example

- 只需等待房主的再讀案例排在進入案例之後，不必等對局案例寫完。

```markdown
1. BE-1.1
2. BE-1.2
3. BE-10.1
```

## Bad Example

- 順序依章節編號排列，把需要對局中 Fixture 的案例排在該 Fixture 尚未建立的案例之前，且漏列拆出的原子案例。

```markdown
1. BE-1.1
2. BE-2.4
3. BE-8.1
```

# Rule 6 - 重複單元

- 介面、Fixture、情境與案例的數量必須依需求範圍增減。
- 增減任一單元時，必須保留骨架中該單元的欄位與層級。
- 不得省略案例欄位，也不得新增骨架沒有的案例欄位。

## Good Example

- 需求只有一個後端介面與兩個案例時，仍保留每個案例的十個欄位。

```markdown
1. **案例 ( Case )** BE-1.1 建立房間
   - **唯一測試意圖 ( Intent )** 不存在的房號會開出房間。
   - **受測部位 ( Subject )** 後端房間 API
   - **受測操作 ( Operation )** `POST /api/rooms/enter`
   - **前置條件 ( Arrange )** Fixture 空資料庫。
   - **操作 ( Act )** `nickname` 為「玩家A」，`roomCode` 為「1234」。
   - **觀測通道 ( Observation Channel )** 這次進入的回應。
   - **預期輸出 ( Expected Output )** HTTP 201。`role` 為房主。
   - **必須維持不變 ( Must Stay )** 無。
   - **本案例不驗證 ( Not Verified )** 第二位玩家。
   - **預期 RED 原因 ( Expected Red )** 進入回應不是 HTTP 201 的房主。
```

## Bad Example

- 案例只留下意圖與預期，省略操作、觀測通道與預期 RED 原因。

```markdown
1. **案例 ( Case )** BE-1.1 建立房間
   - **唯一測試意圖 ( Intent )** 不存在的房號會開出房間。
   - **預期輸出 ( Expected Output )** HTTP 201。
```
