# Rule 1 - 測試描述公開行為

- 測試必須透過公開介面驗證呼叫者在意的行為。
- 測試名稱必須寫出該能力是什麼。
- 一個測試必須只包含一個邏輯斷言。
- 實作結構改變而公開行為不變時，測試必須仍然通過。

## Good Example

- 測試名稱寫出結帳能力，斷言只看公開結果。

```typescript
test("user can checkout with valid cart", async () => {
  const cart = createCart();
  cart.add(product);
  const result = await checkout(cart, paymentMethod);
  expect(result.status).toBe("confirmed");
});
```

## Bad Example

- 同一結帳情境改斷言內部函式的呼叫次數，名稱描述的是做法。

```typescript
test("checkout calls paymentService.process once", async () => {
  await checkout(cart, payment);
  expect(paymentService.process).toHaveBeenCalledTimes(1);
});
```

# Rule 2 - 禁止實作耦合

- 測試不得模擬自己擁有的類別、模組或內部協作物件。
- 測試不得呼叫私有方法。
- 測試不得以公開介面以外的旁路驗證結果。
- 重構後行為不變而測試失敗時，必須把該測試視為實作耦合。
- 改寫耦合測試必須在 Phase 11 進行，並說明耦合原因。

## Good Example

- 建立使用者之後，透過取得使用者的公開介面驗證結果。

```typescript
test("createUser makes user retrievable", async () => {
  const user = await createUser({ name: "Alice" });
  const retrieved = await getUser(user.id);
  expect(retrieved.name).toBe("Alice");
});
```

## Bad Example

- 同一建立使用者行為改查資料庫，驗證路徑繞過公開介面。

```typescript
test("createUser saves to database", async () => {
  await createUser({ name: "Alice" });
  const row = await db.query("SELECT * FROM users WHERE name = ?", ["Alice"]);
  expect(row).toBeDefined();
});
```

# Rule 3 - 禁止同義反覆

- 期望值必須來自獨立依據：已知正確的字面值、算過的範例或規格。
- 期望值不得用與實作相同的算法在測試內再算一次。
- 測試不得斷言某個常數等於自己，也不得使用以相同算法手工製成的快照。

## Good Example

- 總和的期望值是獨立的字面值 15。

```typescript
test("calculateTotal sums line items", () => {
  expect(calculateTotal([{ price: 10 }, { price: 5 }])).toBe(15);
});
```

## Bad Example

- 同一總和情境用與實作相同的 reduce 算出期望值，測試無法與實作分歧。

```typescript
test("calculateTotal sums line items", () => {
  const items = [{ price: 10 }, { price: 5 }];
  const expected = items.reduce((sum, item) => sum + item.price, 0);
  expect(calculateTotal(items)).toBe(expected);
});
```

# Rule 4 - 一次一個垂直切片

- 測試必須一次只寫本輪這一條，並在該測試的實作完成後，才寫下一條。
- 測試不得在實作尚未回應上一輪之前，先把全部案例寫完。
- 下一條測試必須回應上一輪實作所揭露的行為。

## Good Example

- 本輪只提交一條結帳測試，下一條等待這輪實作的結果。

```typescript
test("user can checkout with valid cart", async () => {
  const result = await checkout(cart, paymentMethod);
  expect(result.status).toBe("confirmed");
});
```

## Bad Example

- 同一結帳接縫在實作前一次寫完全部案例，後續測試沒有回應上一輪。

```typescript
test("user can checkout with valid cart", async () => {
  const result = await checkout(cart, paymentMethod);
  expect(result.status).toBe("confirmed");
});

test("user cannot checkout with empty cart", async () => {
  const result = await checkout(emptyCart, paymentMethod);
  expect(result.status).toBe("rejected");
});
```

# Rule 5 - 系統邊界的認定

- 外部 API、資料庫、時間、隨機性與檔案系統必須認定為系統邊界。
- 自己擁有的類別、模組與內部協作物件不得認定為系統邊界。
- 本輪接縫的觀察點跨越上述系統邊界時，必須將該接縫判定為跨越系統邊界。

## Good Example

- 結帳必須呼叫外部付款 API，觀察點跨越系統邊界。

```text
接縫：checkout(cart, paymentMethod)
觀察點：外部付款 API
判定：跨越系統邊界
```

## Bad Example

- 同一結帳流程把內部的價格計算模組也標成系統邊界。

```text
接縫：checkout(cart, paymentMethod)
觀察點：內部 priceCalculator
判定：跨越系統邊界
```
