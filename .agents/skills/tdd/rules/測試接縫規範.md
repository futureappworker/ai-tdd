# Rule 1 - 接縫是公開邊界

- 接縫必須是呼叫者觀察行為所用的公開介面。
- 測試的觀察點必須是該接縫。

## Good Example

- 結帳測試的觀察點是 checkout 這個公開介面。

```typescript
test("user can checkout with valid cart", async () => {
  const result = await checkout(cart, paymentMethod);
  expect(result.status).toBe("confirmed");
});
```

## Bad Example

- 同一結帳行為改以內部的 sumLineItems 作為觀察點。

```typescript
test("checkout totals the cart with sumLineItems", () => {
  expect(sumLineItems(cart.lines)).toBe(15);
});
```

# Rule 2 - 確認後才可寫測試

- 撰寫任何測試之前，必須先列出候選接縫並取得使用者確認。
- 未取得使用者確認的接縫不得寫測試。
- 每條候選接縫必須標明公開介面。
- 每條候選接縫必須以一行說明它抓到的行為，並以一行說明它漏掉的行為。
- 公開介面的形狀尚未確定時，提案仍必須寫出建議的公開介面、抓到的行為與漏掉的行為，並等待使用者確認。

## Good Example

- 提案先寫出介面與抓漏範圍，確認後才進入測試。

```text
接縫：checkout(cart, paymentMethod) -> status
抓到：有效購物車可以完成結帳
漏掉：付款被拒與空購物車
狀態：等待使用者確認
```

## Bad Example

- 介面尚未確認就直接寫測試，違反確認後才可寫測試。

```typescript
test("user can checkout with valid cart", async () => {
  const result = await checkout(cart, paymentMethod);
  expect(result.status).toBe("confirmed");
});
```

# Rule 3 - 沿用領域語言與既有決策

- 接縫名稱與測試名稱必須使用已讀到的 `GLOSSARY.md` 詞彙。
- 接縫提案不得與修改範圍內已讀到的 ADR 衝突。

## Good Example

- 詞彙表將完成訂單稱為 checkout，測試名稱沿用該詞。

```typescript
test("user can checkout with valid cart", async () => {
  const result = await checkout(cart, paymentMethod);
  expect(result.status).toBe("confirmed");
});
```

## Bad Example

- 同一行為改用詞彙表以外的 submitOrder，接縫名稱偏離已讀到的領域語言。

```typescript
test("user can submitOrder with valid cart", async () => {
  const result = await submitOrder(cart, paymentMethod);
  expect(result.status).toBe("confirmed");
});
```

## Exceptions

- 當專案沒有 `GLOSSARY.md` 時，接縫名稱與測試名稱必須使用使用者需求中的行為名稱。
- 當修改範圍內沒有 ADR 時，接縫提案可以不引用 ADR。
